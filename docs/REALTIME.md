# Обновления локальной доски без перезагрузки

Статус: согласуемый проект следующего этапа. Сейчас работают HTTP-чтение,
порционная загрузка карточек и сообщения Sonner. WebSocket, перемещение
карточек и публикация событий ещё не реализованы. Синхронизация с Kaiten
остаётся отдельной задачей из [SYNCHRONIZATION.md](SYNCHRONIZATION.md).

## Разделение команд и событий

Начальную структуру и карточки получаем по HTTP. Будущую команду перемещения
также отправляем по HTTP: ID карточки, целевые колонка/дорожка, положение,
ожидаемая `version` и уникальный `commandId` для повторов. Сервер проверяет
доступ и допустимость перемещения, атомарно сохраняет изменение и увеличивает
версию. При конфликте возвращает 409 с актуальными данными; клиент откатывает
предварительное перемещение и показывает Sonner-сообщение.

WebSocket доставляет уже совершившиеся изменения всем подписанным клиентам.
Он дополняет HTTP и не является условием успешного сохранения команды.
Собственное перемещение можно предварительно показать через кеш TanStack Query,
затем подтвердить ответом сервера. У других пользователей изменение появится
по событию без перезагрузки страницы.

## Контракт событий

Подписка относится к конкретной доске и проверяет права пользователя.
Событие содержит `schemaVersion`, упорядоченный `eventId`, `type`, `boardId`,
`cardId`, `version`, `commandId` и при перемещении старые/новые
`columnId`/`laneId`. Типы: `card.created`, `card.updated`, `card.moved`,
`card.archived`, `card.deleted`, `board.structure.updated`.
ID — UUID/строки, порядок — точная десятичная строка.

На первом этапе событие инвалидирует кеш затронутых ячеек по
`cardKeys.board(boardId)` с уточнением старой и новой ячейки; сервер повторно
отдаёт актуальные страницы. Так обложки, теги, порядок и пагинация останутся
согласованными. Счётчики и уже загруженные порции тоже должны обновляться.
Далее можно применять готовый `CardPreview` к кешу, проверяя версию.
Повторные события отбрасываются по `eventId` и версии карточки.

## Надёжность и несколько процессов

Изменение карточки и запись события в таблицу outbox выполняются одной
транзакцией PostgreSQL. Все пути записи, включая будущий импорт/синхронизацию,
должны использовать тот же механизм. Публикация до коммита недопустима.
PostgreSQL LISTEN/NOTIFY можно использовать как сигнал о новых записях,
но сами события и курсор остаются в БД. Это позволяет восстановиться после
пропуска сигнала и обслуживать несколько серверных процессов без общего
списка соединений в памяти одного процесса.

При первом подключении нужна согласованная последовательность подписки и
снимка с отметкой потока событий: нельзя потерять изменение между GET и
подпиской. Вариант реализации — установить подписку, буферизовать события,
получить HTTP-снимок с отметкой и применить только более новые события.
Эта отметка относится ко всему потоку доски, а не к курсору страницы карточек.
При переподключении клиент передаёт последний `eventId`; сервер повторяет
события. Если история уже очищена, сообщает `resync_required`, после чего
клиент заново загружает структуру и видимые страницы.

Нужны heartbeat, переподключение с увеличением задержки и случайным смещением,
ограниченная очередь, проверка Origin и авторизация подписки. При потере связи
показываем одно сообщение, после восстановления — одно подтверждение;
не отправляем toast для каждого чужого перемещения. В резервном режиме можно
повторно запрашивать видимые ячейки по HTTP. Постоянный опрос пока не включён.

## Условия готовности

- Две вкладки видят одно сохранённое перемещение без перезагрузки.
- Одновременные команды не перетирают новую версию карточки.
- Повтор команды/события не создаёт дублей.
- Разрыв связи, переподключение и пропуск события восстанавливают состояние.
- Архивация, удаление и перемещение между дорожками обновляют обе ячейки.
- Ошибка команды откатывает предварительное отображение и показывает сообщение.

Основание для реализации: [WebSocket в FastAPI](https://fastapi.tiangolo.com/advanced/websockets/).
Документация отдельно указывает ограничение примера со списком соединений
в памяти одним процессом. Сообщения клиента: [Sonner](https://sonner.emilkowal.ski/getting-started).
