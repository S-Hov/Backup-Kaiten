# Архитектура приложения

## Решение: Python остаётся

Python выбран с учётом существующего экспортёра и желания освоить язык на
реальном проекте. Для этой задачи Node.js также подходит; переписывание само
по себе не даст проекту более правильную архитектуру. Если единственным
приоритетом станет максимальная скорость разработки знакомой командой на
TypeScript, выбор можно пересмотреть. Текущий контракт API это допускает.

Сервер — FastAPI, данные — SQLAlchemy, миграции — Alembic. Для локального
запуска без Docker доступен SQLite; Docker Compose использует PostgreSQL 18.
Начинаем с модульного монолита: один сервер и одна БД, без набора
микросервисов. Обычные синхронные функции и транзакции проще изучать и отлаживать;
FastAPI выполняет такие HTTP-обработчики в пуле потоков.

Запуск контейнеров описан в [DOCKER.md](DOCKER.md). Предложение нормализованной
модели рабочей доски на основе сохранённых ответов API — [DATABASE_DESIGN.md](DATABASE_DESIGN.md).
Существующие архивные SQL-таблицы пока сохраняются без изменения назначения.

Клиент отделён в `frontend/`. Пока сохранён работающий компонент Web Components
и ES-модули: переносить его на React только ради названия фреймворка не нужно.
Когда появятся редактируемая доска и сложное состояние интерфейса, React с
TypeScript можно внедрять отдельно, сохраняя API и модель карточки.

## Границы ответственности

```text
frontend/api.js → HTTP /api/v1 → api/routes.py
                                    ↓
                             application/CardService
                                ↙           ↘
                       CardRepository   AttachmentStorage
                         ↙      ↘             ↓
                  JSON-архив    SQL         файлы на диске
```

- HTTP-слой валидирует запросы и возвращает ответы; не читает JSON напрямую.
- Сценарий `CardService` получает репозиторий через интерфейс. Ему не важно,
  сохранены карточки в папках или таблицах.
- Подготовка `CardViewModel v1` отделена от хранения. Дополнительные поля
  оригинальных JSON не теряются: они остаются в `raw`.
- Компонент `KaitenCard` получает объект данных и рисует форму. Обращения к
  серверу сосредоточены в `frontend/api.js`.
- Вложения проходят через отдельный интерфейс хранения. Позже локальный диск
  можно заменить S3-совместимым хранилищем.
- Экспорт из Kaiten остаётся независимой командой; HTTP-запрос не запускает
  длительную массовую выгрузку или импорт.

Приложение собирается в `create_app()`: там выбираются зависимости и режим
хранения. Это позволяет тестировать один и тот же API с архивом и БД.

## Архив и рабочая доска — разные данные

Текущая миграция создаёт `archive_snapshots` и `archive_cards`. Она предназначена
для сохранения исторических копий, а не имитирует все внутренние таблицы Kaiten.
Ключ карточки: `(snapshot_id, card_id)`. Один заказ в разных снимках не
перезаписывает другую историческую версию.

JSON-разделы сохраняются целиком. Заголовок, номер, колонка, архивность и
нормализованный текст поиска вынесены в отдельные колонки. Это позволяет
переключить существующий просмотрщик на БД без потери исходного материала.
Поиск использует буквальный подстрочный запрос; `%` и `_` не становятся
пользовательскими SQL-шаблонами. Для больших объёмов следующим улучшением будет
PostgreSQL full-text/trigram-поиск по согласованным полям.

Редактируемая доска должна получить **отдельные** сущности `boards`, `columns`,
`cards`, `users`, `memberships`, `comments`, `attachments`, `card_events`.
Нельзя использовать неизменяемый архив как источник редактируемого состояния.
Первый импорт в рабочую доску должен иметь явное сопоставление исходных ID и
новых внутренних ключей, повторяемость и отчёт о неполных данных.

Бинарные вложения в БД не помещаем. В будущей таблице храним ключ объекта,
имя, размер, MIME, контрольную сумму, владельца и права. В начальном SQL-режиме
оригиналы всё ещё читаются из папки архива — полная независимость от неё пока
не реализована.

## Что уже работает

1. Чтение архива, поиск и просмотр карточек через FastAPI.
2. Версионированный HTTP API и OpenAPI-спецификация без внешних CDN.
3. SQL-репозиторий, первая миграция, повторяемый пакетный импорт.
4. Тот же компонент карточки с обоими источниками данных.
5. Отдельные настройки, виртуальное окружение, фиксированные зависимости и CI.

## Следующие этапы

Обновление данных из Kaiten отложено до готовности БД и полноценного
веб-интерфейса. Основным выбран периодический опрос API; External Webhooks
оставлен альтернативой. Решение и критерии проверки описаны в
[SYNCHRONIZATION.md](SYNCHRONIZATION.md). Системы обновлений в текущем коде нет.

1. Проверить PostgreSQL в реальной среде и импорт всего архива, сверить числа,
   проблемы и контрольные суммы вложений.
2. Добавить модели рабочей доски и отдельную команду переноса архивных заказов.
3. Реализовать создание и изменение карточек, перемещение между колонками,
   комментарии и загрузку файлов. Добавить транзакции и оптимистическую
   блокировку по версии, чтобы пользователи не перетирали изменения друг друга.
4. Добавить вход, роли, проверки прав на сервере и журнал действий.
5. После этого — размещение с HTTPS, управлением секретами, резервными копиями,
   мониторингом и отдельным хранением вложений. WebSocket-обновления нужны,
   когда появится реальная одновременная работа, не раньше.

Пока сервер намеренно слушает loopback и не позиционируется как готовая
многопользовательская система. CI проверяет SQLite; PostgreSQL требуется
отдельная интеграционная проверка.

Официальные материалы: [структура FastAPI](https://fastapi.tiangolo.com/tutorial/bigger-applications/),
[жизненный цикл SQLAlchemy Session](https://docs.sqlalchemy.org/en/20/orm/session_basics.html),
[миграции Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html).
