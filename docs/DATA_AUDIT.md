## Собственные и исходные ID

Внешний номер не используется как единственный первичный ключ:

- `id` — собственный UUID. Все связи рабочих таблиц используют UUID.
- `source_id` — исходный ID Kaiten, сохраняется отдельно, без изменения.
- `source_instance_id` — компания/источник (`source_instances.origin`).
- `source_uid`, исходные даты/версия и `source_data` сохраняют дополнительные
  идентификаторы и исходные поля.

Для импортируемых объектов UUID детерминированно вычисляется через UUIDv5 из
источника, типа сущности, исходного ID и при необходимости контекста карточки.
Повторный импорт той же записи получает тот же UUID. Одинаковые номера из
разных компаний или типов сущностей не смешиваются. Локальные записи получают
собственные UUID без искусственного ID Kaiten.

`display_number` у карточки — номер для интерфейса, не ключ внешних связей.
`accounts.id` и `accounts.user_id` — разные UUID: аккаунт входа связан с профилем,
который уже используется участниками, комментариями и историей.

## Где лежат файлы и откуда получены данные

`file_objects.storage_key` хранит ключ фактического файла, `size`, `mime_type`,
`sha256`, `hash_verified` — метаданные. Для импортированного вложения ключ
относителен корню `backups`, например `имя_снимка/cards/123/files/макет.png`.
Новые локальные файлы имеют ключ `local-upload:UUID` и лежат в томе `uploads`.
Таблица `attachments` связывает файл с карточкой, комментарием/полем и автором;
её `source_data` содержит исходные данные, манифест и снимок.

`archive_snapshots` содержит сведения снимка и справочники. `archive_cards`
сохраняет исходные разделы JSON в БД, а не только пути к ним. Дополнительно
`source_records` явно связывает UUID карточки с `cards/ID/card.json`, а профиль
из справочника — с `board/users.json` и индексом записи. Это происхождение
импортированных данных, а не актуальный источник локальных изменений.
Индивидуальное происхождение каждого поля и каждого комментария эта таблица
пока не отслеживает; соответствующие разделы доступны в SQL raw и source_data.

```powershell
docker compose run --rm --no-deps tools enrich-existing
```

Команда заполняет новые колонки профилей и происхождение по уже сохранённым
SQL-данным. Не читает JSON-папки карточек, не запускает экспорт, не создаёт
учётных записей и не перезаписывает рабочие карточки. Повторный запуск безопасен.
Обычный `update-board` теперь выполняет это обогащение после успешного обновления.
