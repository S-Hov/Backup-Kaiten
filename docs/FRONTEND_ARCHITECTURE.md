# Архитектура клиента: FSD и работа с API

Статус: архитектура согласована, базовый переход выполнен 27.10.2026.
Реализованы слои app/pages/widgets/entities/shared, общий HTTP-клиент со схемами,
React Router и проверка границ импортов в CI. Главная страница читает структуру
доски из рабочих SQL-таблиц; архив вынесен в `/archive`. Слой features появится
вместе с пользовательскими операциями. Остальные разделы описывают целевой рост.

## Решение

Для будущей многопользовательской доски подходит Feature-Sliced Design:
разделение по предметным областям и пользовательским действиям, с проверяемыми
направлениями зависимостей. Одни названия папок без этих правил пользы не дадут.
React, TypeScript, SCSS, Vite, FastAPI и TanStack Query остаются.

Из `\\wsl.localhost\Ubuntu\home\lin\projects\auto-admin` стоит перенять общий
HTTP-клиент, проверку ответов, типизированные ошибки, модули запросов и публичные
интерфейсы. Систему установки, формат ответов и устройство состояния копировать
целиком не предлагается: у нашей доски другие задачи и уже есть свой серверный контракт.
Проект-пример при анализе не изменялся.

В текущем `auto-admin` есть структура `app/pages/widgets/features/shared`, но нет
каталога `entities`. Это не делает проект неправильным: слои вводятся по необходимости.
Для нашей доски отдельные сущности полезны, поскольку карточки, пользователи и доски
будут использоваться на разных экранах.

Некоторые зависимости примера мы исправим при адаптации: например,
`features/install-database/ui/InstallDatabaseForm.tsx` импортирует
`app/providers/bootstrap/BootstrapContext`. У нас фича не должна знать, как
собрано приложение. Координация остаётся выше, а фича получает callback либо
использует публичный API сущности/нижнего слоя.

## Что не переносим буквально

- В примере ответы имеют `success`, `code`, `data`, а ошибки — свою обёртку.
  Наш FastAPI сейчас возвращает данные напрямую и ошибки `{ "error": "..." }`.
  Клиент должен проверять **наш** контракт. Менять все ответы ради структуры
  другого проекта не требуется.
- Вычисление HTTP-адреса через hostname браузера и порт `5180` не подходит нашей
  сборке. Сохраняем относительный `/api/v1`, Vite proxy в разработке и один origin
  в Docker. Kaiten API-токен и пароль БД никогда не становятся `VITE_*` переменными.
- `AuthProvider` и `BootstrapProvider` примера самостоятельно загружают и хранят
  серверные данные через `useEffect/useState`. Кеш досок, карточек и пользователя
  у нас будет в TanStack Query; второй параллельный кеш в Context не нужен.
- Установщик БД, токен установки, редактор произвольной админской системы и
  каталог сторонних иконок не относятся к текущему продукту.
- Не переносим CSS всех экранов в глобальные стили и не заводим отдельный модуль
  на каждую из 30 таблиц PostgreSQL. Границы фронтенда определяются продуктом.

## Направление зависимостей

```text
app → pages → widgets → features → entities → shared
```

Зависимости направлены вниз; слой может пропускать промежуточные слои.
Это базовое правило [FSD](https://feature-sliced.design/docs/reference/layers).
Слои добавляются по задаче — не нужно заранее создавать пустые каталоги.

Наши правила:

1. Соседние slices одного слоя не импортируют друг друга. Две фичи объединяет
   виджет или страница; два виджета — страница.
2. Внешний код использует публичный `index.ts` slice. Внутри slice допустимы
   относительные импорты; импорт собственного barrel-файла избегаем ради циклов.
   Это соответствует роли [публичного API FSD](https://feature-sliced.design/docs/reference/public-api).
3. В `shared` нет импортов `Card`, `Board`, `Person` и прочих бизнес-сущностей.
   Общий Avatar принимает, например, текст/изображение; `UserAvatar` знает профиль
   и находится в `entities/user`.
4. `app` и `shared` не делятся на бизнес-slices. В `shared` публичные входы
   организуем по назначению: `shared/api`, `shared/ui/button`, `shared/lib/date`.
   Единого `shared/index.ts`, экспортирующего весь проект, не создаём.
5. Не используем `export *` для публичных границ: явно перечисляем нужные функции,
   типы и компоненты. Общие типы не превращаются в глобальный файл на тысячи строк.
6. Для редкой реальной связи двух сущностей официальный FSD допускает отдельный
   контракт `@x`. Применять его будем адресно и с объяснением; массово разрешать
   любые cross-imports между сущностями не будем.
7. FSD относится к клиенту. Python-сервер сохраняет свои слои application/domain/
   infrastructure, а не переименовывается в `features/entities/widgets`.

## Целевая карта продукта

Это карта размещения будущих частей, а не требование создать всё сразу.

```text
frontend/src/
  app/
    providers/                 QueryClient, обработка сессии, общие провайдеры
    router/                    маршруты, layouts, lazy loading, guards
    styles/                    reset, токены, глобальная типографика
    App.tsx                    сборка приложения

  pages/
    archive/                   существующий просмотрщик резервных копий
    board/                     экран рабочей доски и её URL-параметры
    boards/                    выбор доски/пространства
    settings/                  настройки по мере появления

  widgets/
    archive-browser/           выбор снимка, поиск, список, детали
    card-inspector/            большая карточка с разделами и действиями
    kanban-board/              композиция колонок, карточек и перемещения

  features/
    search-cards/              поиск, если используется в нескольких местах
    filter-board/              пользовательские фильтры рабочей доски
    create-card/               создание
    edit-card/                 редактирование
    move-card/                 перемещение и его оптимистическое состояние
    add-comment/               добавление комментария
    upload-attachment/         загрузка файлов

  entities/
    archive/                   снимок, архивная карточка и её API
    card/                      рабочая карточка, краткое представление, запросы
    board/                     структура доски, колонки и дорожки
    user/                      профили и их отображение
    session/                   текущая сессия/доступные действия

  shared/
    api/                       fetch, ошибки, обработка JSON, общие контракты
      generated/               генерируемые DTO/клиент при внедрении генерации
    config/                    публичные настройки приложения
    routes/                    общие построители адресов
    lib/
      date/                    форматирование дат
      file/                    размеры файлов, общие операции
      rich-text/               очистка HTML и Markdown без знания о Kaiten
      form/                    адаптер ошибок полей, когда появятся формы
    ui/
      button/
      dialog/
      loader/
      json-value/
```

Slice имеет только нужные сегменты `api`, `model`, `ui`, `lib` и публичный `index.ts`.
`features/card` со всей карточкой — слишком широкая граница: карточка является
сущностью, а её редактирование и перемещение — разными действиями.

Для одноразового кода страницы отдельная feature/widget не обязательна. Например,
выбор единственного архивного снимка сначала может оставаться в `pages/archive`.
`widgets` используем для самостоятельных крупных блоков с собственной композицией,
а не для каждой панели и кнопки. Комментарии/чек-листы выделим в самостоятельные
entities только при реальном повторном использовании.

## HTTP, контракты и TanStack Query

Предлагаемая цепочка чтения:

```text
page / widget
    → queryOptions из entities/<domain>/api
        → функция endpoint-а + схема ответа
            → shared/api: fetch и нормализация ошибок
                → FastAPI /api/v1
```

Общий транспорт не вызывает навигацию, toast, `setState` или методы форм и не
импортирует `app`. Он принимает URL, параметры, метод, body, схему и `AbortSignal`.
JSON-заголовок устанавливается только для JSON; границу `multipart/form-data`
формирует сам браузер. Отмена запроса остаётся отменой и не показывается как сбой.

Из auto-admin переносим сам принцип runtime-проверки: запись
`response.json() as Promise<T>` в нашем текущем `api/client.ts` лишь утверждает тип
для TypeScript, а содержимое ответа не проверяет. Нужна схема в точке получения
ответа. Известные поля проверяем без скрытой coercion; дополнительные поля сервера
и неизвестные разделы архива сохраняем. Нарушение успешного контракта — отдельная
`ApiContractError`, а не пустая карточка или автоматически подставленные значения.

Для небольшого текущего API схемы можно описать через Zod и выводить из них типы,
как в примере. Перед расширением рабочего API уточним Pydantic-модели: сейчас
`CardViewModel.card` и `sections` на сервере описаны слишком общими словарями,
поэтому одна генерация из сегодняшнего OpenAPI не восстановит их внутренние типы.
После уточнения моделей вводим генерацию DTO/схем из OpenAPI и проверку расхождений
в CI. Генерируемые файлы не правим вручную; не поддерживаем три независимые
рукописные копии одного DTO в Python, интерфейсе TS и Zod.

У транспортной ошибки нужны `status`, стабильный код при наличии, безопасное
сообщение, детали полей и ID запроса, когда сервер начнёт его отдавать.
Текущий `{error: string}` поддерживаем адаптером. Единый контракт ошибок и детали
422 будем согласовывать с сервером, сохраняя совместимость `/api/v1` либо явно
версионируя несовместимое изменение. Самовольной смены envelope на формат auto-admin нет.

TanStack Query сохраняем. Размещение query factories в `entities/.../api` совместимо
с [рекомендациями FSD для TanStack Query](https://feature-sliced.design/docs/guides/tech/with-react-query).
Вместо ручных ключей в каждом компоненте slice экспортирует, например,
`cardQueries.detail(id)` и `cardQueries.list(filters)`.

Ключ должен однозначно учитывать источник и параметры:

```text
['archive', snapshotId, 'card', kaitenCardId]
['archive', snapshotId, 'cards', { query, offset, limit }]
['working', 'board', boardId, 'cards', normalizedFilters]
['working', 'card', cardId]
```

Разделение ключей — наше правило для двух источников; общие требования к ключам
описаны в [TanStack Query](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys).
Ключи не содержат файлов, больших JSON и секретов. При смене аккаунта кеш прежней
сессии очищается. Фильтры предварительно нормализуются в одном месте.

Изменяющие операции размещаем в соответствующей feature: схема запроса, mutation,
обработка ошибки, обновление/инвалидация затронутых запросов. Низкоуровневый вызов
endpoint-а может принадлежать сущности, если нужен разным сценариям.

Для будущих операций записи:

- GET можно ограниченно повторять при временной сети, 429/5xx; 400/401/403/404,
  отмену и ошибки контракта автоматически не повторяем. Политика принадлежит
  QueryClient/сценарию, а не скрытому бесконечному циклу в HTTP-клиенте.
- Создание карточки, комментария или файла не повторяем автоматически без
  поддержанного сервером ключа идемпотентности.
- Перемещение карточки сначала отменяет мешающее чтение, сохраняет состояние для
  отката, оптимистически меняет UI и затем сверяется с ответом сервера. Версия
  записи передаётся серверу; 409 требует разрешения конфликта, а не перезаписи.
- Ошибка чтения показывается рядом с блоком с возможностью повторить. Ошибка
  сохранения — в форме/действии. Транспорт не создаёт несколько toast при retries.
- Будущие события сервера обновляют или инвалидируют эти же query keys. Отдельный
  несогласованный кеш для WebSocket не заводим. Синхронизация Kaiten остаётся
  серверной задачей, а не циклом запросов браузера к Kaiten.

## Архивные и рабочие данные

Архивный номер `14796440` — ID Kaiten, а рабочий `cards.id` — UUID.
Не объединяем их типом `string | number` и не предполагаем, что номер уникален
между разными компаниями/снимками.

`entities/archive` отвечает за существующие `/snapshots`, `/cards?snapshot=...`
и старый `CardViewModel v1`. `entities/card` будет отвечать за будущий контракт
рабочей карточки. Маршруты рабочего API ещё предстоит реализовать: текущий
`BOARD_STORAGE=database` читает архивные SQL-таблицы, а не новое ядро доски.

Составной `widgets/card-inspector` сможет получить контекст источника и преобразовать
архивный либо рабочий DTO в собственную модель отображения. Архивный просмотр
остаётся только для чтения; кнопки записи зависят от источника и разрешений.
Такая композиция может импортировать обе сущности, не заставляя их импортировать
друг друга. Один компонент отображения не означает одинаковый контракт хранения.

Состояние разделяем:

| Вид | Где хранить |
| --- | --- |
| Карточки, доски, комментарии, сессия | TanStack Query |
| Доска, выбранная карточка, фильтры/поиск, если ими делятся ссылкой | Router / URL |
| Черновик формы, валидация, серверные ошибки полей | Состояние feature; React Hook Form при появлении форм |
| Открытая вкладка, диалог изображения | Локальное состояние UI |
| Временное состояние drag-and-drop | Feature перемещения; отдельное хранилище только при реальной необходимости |

Zustand/Redux не добавляются заранее. Context остаётся для зависимостей и
действительно общего UI-состояния, а не для копии всех данных сервера.
Права интерфейса отражают возможности пользователя; обязательная проверка доступа
всегда выполняется сервером.

## Стили и размеры данных

SCSS сохраняем. Общие токены, reset и типографика — `app/styles`;
стили компонентов постепенно переводим в `*.module.scss` рядом с UI. Первый
переход структуры не должен одновременно менять все классы и внешний вид.

Экран рабочей доски не должен загружать подробные JSON всех 20 тысяч карточек.
Нужны лёгкие списки/порции колонок, отдельная загрузка подробностей и лент,
ленивые изображения и сохранение позиции прокрутки. Виртуализацию добавляем
для измеренного большого списка. Это свойства API и отображения, одной FSD
проблему объёма не решить.

Общий sanitizer в `shared/lib/rich-text` получает разрешённый способ разрешения
картинок извне; привязка URL Kaiten к архивному вложению остаётся у архивного
адаптера/виджета. Так Shared не становится зависимым от формата резервной копии.

## Как переложить текущие файлы

| Сейчас | Целевое размещение |
| --- | --- |
| `src/app/App.tsx` с выбором архива, поиском и запросами | `pages/archive` и при необходимости `widgets/archive-browser`; в App остаётся сборка |
| QueryClient в `src/main.tsx` | `app/providers/query`; main только монтирует приложение |
| `src/api/client.ts` | Общий transport в `shared/api`, архивные endpoints — в `entities/archive/api` |
| `src/api/types.ts` | Архивные схемы/типы в `entities/archive`; общие JSON/transport-типы — в Shared |
| `features/cards/CardDetails.tsx` | `widgets/card-inspector/ui`, поскольку это композиция большого числа разделов |
| `features/cards/Discussion.tsx` | Внутренний UI card-inspector до необходимости переиспользования |
| `features/cards/Attachments.tsx` | Сначала UI card-inspector; общие Dialog/Preview-примитивы отдельно в shared/ui |
| `shared/components.tsx` | Общие Empty/Disclosure/JsonValue — по назначению в shared/ui; пользовательский Avatar — entity/UI adapter |
| `shared/format.ts` | Даты/размеры — shared/lib, вычисления из профиля — entities/user или архивный адаптер |
| `src/styles` | Базовые app/styles; дальнейшая локализация SCSS по компонентам |

Не копируем весь `src` auto-admin поверх нашего. Не создаём скрытый универсальный
`BaseRepository<T>` на клиенте: важнее явные функции endpoint-ов и пользовательские
операции. Не меняем API, UI, структуру и стратегию состояния одним большим коммитом.

## Порядок внедрения и критерии готовности

1. **Границы:** перенести текущий просмотрщик без изменения поведения. Ввести
   алиас `@/`, публичные входы и автоматические проверки импортов: запрет вверх,
   запрет между slices одного уровня, запрет обхода публичного API и циклов.
   Исключения для тестов и генерируемого кода делаются явно.
2. **Транспорт:** схемы ответов, типизированные ошибки, отдельные архивные endpoints
   и query factories. Проверить 200 с неверным JSON, HTTP-ошибки, отмену, сеть,
   дополнительные поля и отсутствие незаметных преобразований.
3. **Навигация:** страницы архива/доски и React Router, совместимость существующих
   ссылок `?snapshot=...&card=...`, URL-фильтры и возврат к прежнему положению списка.
4. **Рабочий API:** реализовать чтение нормализованных таблиц и уточнённые серверные
   схемы. Подключать его к отдельной entity, не переименовывая архивный контракт.
5. **Запись:** по одной feature — сначала изменение карточки, затем перемещение,
   комментарии/файлы. Включить проверки версий, права, формы и целевое обновление кеша.

На каждом этапе остаются рабочими поиск, выбор копии, отмена устаревшего запроса,
открытие карточки, вложения, история и неизвестные JSON-разделы. Проверяются
TypeScript, компонентные тесты, сборка Vite и Docker. Для API добавляются
контрактные тесты с серверными примерами. Сохранение сырого JSON не означает,
что он автоматически становится типизированной редактируемой моделью.

Новый импорт и синхронизация не запускаются из-за изменения структуры фронтенда.
