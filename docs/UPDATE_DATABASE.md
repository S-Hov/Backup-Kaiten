# Обновление рабочей базы из JSON

`update_database.py` читает уже сохранённый архив и обновляет **рабочие таблицы**
доски. Запросов к Kaiten нет, API-токен не нужен. Исходные JSON и файлы не меняются.
Это отдельная команда от старого `import-archive`, который заполняет только архивные
SQL-таблицы. Автоматический запуск, синхронизация и переключение интерфейса не включены.

## Docker: рекомендуемый способ

После изменения кода пересоберите образ:

```powershell
docker compose build tools
```

Сначала посмотреть объём работы, без подключения к базе и без изменений:

```powershell
docker compose run --rm tools update-board --snapshot "2026-10-22_08-58-24_447787Z_board_437516" --plan
```

Обработать одну карточку, затем при необходимости весь снимок:

```powershell
docker compose run --rm tools update-board --snapshot "2026-10-22_08-58-24_447787Z_board_437516" --card-id 14796440 --verify-files
docker compose run --rm tools update-board --snapshot "2026-10-22_08-58-24_447787Z_board_437516"
```

Compose применяет миграции перед запуском команды. В частности, `0003_sort_order`
расширяет порядок карточек/колонок до `numeric(50,25)`: реальные значения Kaiten
содержат более десяти дробных знаков. Скрипт откажется записывать их в старую схему,
чтобы PostgreSQL не округлял их молча. Архивные записи не преобразуются этой миграцией.

**Эти команды записи приведены для явного запуска пользователем. При разработке
массовое наполнение основной рабочей базы не выполнялось.**

## Запуск без Docker

Используются настройки приложения: `BOARD_BACKUP_ROOT`, `BOARD_DATABASE_URL` и
при необходимости `BOARD_DATABASE_PASSWORD_FILE`. При отсутствии URL локальный
запуск использует `.local/board.db` (SQLite), а не PostgreSQL контейнера.
У PostgreSQL в обычном Compose нет опубликованного порта — используйте команду
в контейнере выше, если целевая база именно там.

```powershell
.\.venv\Scripts\python.exe -m backend.app.cli migrate
.\.venv\Scripts\python.exe update_database.py --snapshot "2026-10-22_08-58-24_447787Z_board_437516" --card-id 14796440 --plan
.\.venv\Scripts\python.exe update_database.py --snapshot "2026-10-22_08-58-24_447787Z_board_437516" --report ".local/update-report-001.json"
```

## Флаги

| Флаг | Назначение |
| --- | --- |
| `--snapshot NAME` | Обязательное имя папки снимка в каталоге копий |
| `--card-id ID` | Одна карточка; можно повторить для нескольких |
| `--limit-cards N` | Ограничить число карточек (по убыванию ID) |
| `--batch-size N` | Сколько карточек фиксировать одной транзакцией; 50 по умолчанию, максимум 1000 |
| `--backup-root PATH` | Другой каталог JSON-архивов |
| `--origin URL` | Адрес компании, если его нет в `report.json`; обычно определяется автоматически |
| `--plan` | Только объём работы и ID, без подключения к БД; не предсказывает число INSERT/UPDATE |
| `--verify-files` | Дополнительно читать содержимое вложений и проверять SHA-256 |
| `--overwrite-local` | Явно разрешить перезапись локальных правок (`local_version > 1`); более старые версии источника всё равно не применяются |
| `--report PATH` | Дополнительно записать JSON-отчёт; путь вне исходного архива, файл не должен уже существовать |

Частота API-запросов здесь не настраивается: API вообще не используется.
Размер пакета управляет транзакциями; параллельное чтение/запись пока не включены.
На Windows чтение множества мелких файлов через Docker bind mount может быть медленным.
Существующий `scripts/import_docker_archive.py` пока относится к старому архивному
импорту и не заменяет `update-board`.

## Что переносится

- Доска, колонки/подколонки, дорожки, типы, профили пользователей, теги,
  определения и варианты пользовательских полей.
- Карточки и их поля, участники/подписки, назначения тегов, значения свойств.
- Комментарии с форматами и признаками удаления, чек-листы и пункты,
  родительские/дочерние связи, блокировки, внешние ссылки.
- История расположения и события с исходными данными. Исторические имена и
  расположение не перезаписывают текущие справочники.
- Метаданные вложений и физического файла. Файлы остаются в исходном архиве;
  `storage_key` содержит имя снимка и относительный путь. По умолчанию проверяется
  существование, безопасный путь и размер; SHA-256 читается с `--verify-files`.
  Отсутствующий/повреждённый файл отмечается `missing` с предупреждением.
- Все исходные JSON-разделы, включая неизвестные и пока не нормализованные
  (`time-logs`, `iterations`, `baselines`, `sla`), сохраняются в архивных таблицах.

Локальные аккаунты, пароли, роли и права из числовых ACL Kaiten не создаются.
Пространства/размещение досок не выдумываются, если в экспорте нет этих сведений.
Ссылки на ещё не выгруженные карточки/пользователей становятся помеченными
неполными записями (`is_stub`). Для карточки с неизвестной доской используется
отдельная неполная доска, а не предположение о принадлежности текущей.

## Обновления, ошибки и повторный запуск

Идентификатор источника — адрес компании, объект определяется внешним ID внутри
этого источника. UUID рабочей записи остаётся прежним. Повторный запуск не добавляет
дубли. Файл с ID, отличающимся от имени папки, не применяется.

Отсутствующее поле карточки не очищает существующее значение. Отсутствующий или
повреждённый JSON-раздел не удаляет ранее сохранённые комментарии/участников;
его предыдущая архивная версия сохраняется с замечанием. Явный пустой список тегов,
участников или отношений обновляет соответствующие связи. Само отсутствие объекта
в снимке не означает удаление: комментарии/вложения/пункты помечаются удалёнными
только по явному признаку источника. Циклы иерархии отклоняются.

Скрипт пропускает карточку при более старой версии/дате либо конфликте локальных
правок. Ошибка одной карточки откатывает её изменения, включая связи и архивный
JSON; остальные карточки продолжают обрабатываться. Справочники обновляются одной
начальной транзакцией: ошибка или конфликт в них останавливает запуск до карточек.
После сбоя уже зафиксированные пакеты сохраняются. Повторите команду для продолжения;
checkpoint-файл не нужен, поскольку операции повторяемы.

На PostgreSQL advisory lock запрещает два одновременных обновления одной компании.
Механизма конфликтов двусторонней синхронизации этот скрипт не реализует.

Прогресс выводится в stderr, итоговый JSON — в stdout: `planned_cards`, `saved`,
`errors`, `conflicts`, `warnings`, статус исходной копии, время запуска/окончания.
`saved` — число успешно обработанных карточек, включая повторно проверенные,
а не число новых строк. При пустой рабочей базе связи могут создавать больше
записей карточек за счёт неполных родителей/детей; это ожидаемо и видно по `is_stub`.

Коды завершения: 0 — обработка закончена без ошибок/конфликтов (предупреждения
нужно смотреть в отчёте), 2 — есть ошибки карточек или конфликты, 1 — запуск
невозможен из-за настроек, схемы, справочников или соединения. Исходный `partial`
не выдаётся за полную резервную копию после успешного чтения.

Интерфейс после выполнения команды остаётся в прежнем режиме чтения JSON.
Режим `BOARD_STORAGE=database` читает архивные SQL-таблицы; переход на рабочие
таблицы — отдельный следующий шаг.
