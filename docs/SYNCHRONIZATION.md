# Обновление локальной доски из Kaiten

Дата решения: **26 октября 2026 года**.

**Статус: согласованный подход для будущей реализации. Система обновлений пока
не реализуется.** К разработке возвращаемся после готовности PostgreSQL,
рабочей модели доски и полноценного веб-интерфейса.

## 1. Принятое решение

- **Основной вариант № 1:** периодически запрашивать изменения через API Kaiten.
- **Альтернативный вариант № 2:** получать External Webhooks. Сохраняем как
  возможное развитие, сейчас не подключаем.
- На переходном этапе направление синхронизации — **Kaiten → наша система**.
  Kaiten остаётся главным источником рабочих данных.
- Задача — обновлять созданные и изменённые карточки, связанные сведения и
  вложения, не скачивая заново содержимое всех карточек доски.
- Текущие данные, история импорта и резервные копии хранятся раздельно.

Двусторонняя синхронизация в это решение не входит. Для одновременного
редактирования одной карточки в двух системах потребуются отдельные правила
разрешения конфликтов и защиты от циклических обновлений.

## 2. Вариант № 1 — периодический опрос API, выбран основным

### Возможности Kaiten

Метод получения списка карточек поддерживает `updated_after`, `updated_before`,
`board_id`, `condition`, `limit` и `offset`. Даты передаются в формате ISO 8601;
максимальная страница списка — 100 карточек. `condition=1` выбирает карточки
на доске, `condition=2` — архивные.

Источник: [список карточек Kaiten](https://developers.kaiten.ru/cards/retrieve-card-list).

Пример запроса для нашей доски, иллюстрирующий параметры:

```http
GET /api/v1/cards?board_id=437516&version=1&condition=1&updated_after=2026-10-26T09:00:00Z&updated_before=2026-10-26T09:01:00Z&limit=100&offset=0
```

Архивные карточки запрашиваются отдельно с `condition=2`. Для следующей
страницы увеличивается `offset`. Заголовок авторизации передаётся сервером;
токен не должен попадать в URL, клиентское приложение или журнал запросов.

### Последовательность работы

1. Фоновый процесс начинает цикл и фиксирует временное окно поиска изменений.
2. Получает все страницы изменённых активных и архивных карточек.
3. Сохраняет найденные ID в устойчивую очередь задач в PostgreSQL.
4. Для каждого ID получает актуальную подробную карточку и выбранные связанные
   разделы: комментарии, участников, чек-листы, историю, файлы и т. д.
5. Обновляет соответствующие записи рабочей БД. Повторная обработка того же
   состояния не создаёт дубликаты.
6. Сравнивает метаданные вложений; повторно использует уже сохранённые
   неизменившиеся файлы, скачивает новые и изменившиеся.
7. Фиксирует результат обработки и сведения об ошибках. В интерфейсе видно,
   когда карточка синхронизировалась и есть ли недостающие данные.

Получение списка изменений и применение этих изменений — разные этапы.
Ошибка одного вложения не должна блокировать обновление всех остальных заказов.

### Периодичность и временные границы

Предварительные настройки для начала испытаний:

| Настройка | Начальное предложение |
| --- | --- |
| Интервал проверки | 60 секунд |
| Перекрытие временных окон | 3 минуты |
| Задержка верхней границы относительно текущего времени | 30 секунд |
| Общая скорость API-запросов | Начать с текущих 3 запросов в секунду |
| Внутреннее хранение времени | UTC |

Это настройки нашего будущего сервиса, **не гарантии или требования Kaiten**.
Они уточняются после проверки задержек, нагрузки и поведения API.

Обозначения: `W` — сохранённая граница успешно обнаруженных изменений,
`T` — верхняя граница нового окна. Запрашиваем изменения примерно за интервал
`W − перекрытие … T`, сохраняя одинаковые границы на всех страницах цикла.
Точное включение крайних дат нужно проверить на API; обработка повторов должна
делать перекрытие безопасным. Часы серверов должны быть синхронизированы.

**Нельзя сдвигать `W` просто потому, что таймер сработал.** Границу обнаружения
можно продвинуть после успешного обхода всех страниц и надёжного сохранения
задач в БД. Если хотя бы страница не получена, окно повторяется.

Сохранённые задачи обрабатываются независимо и повторяются после ошибок.
Продвинутая граница обнаружения не означает, что все карточки уже обновлены:
задолженность очереди и ошибки должны учитываться отдельно. Если в реализации
не будет устойчивой очереди, границу нельзя продвигать до завершения обработки
всего окна.

Перекрытие снижает риск пропусков, но само по себе не гарантирует полноту при
длительных задержках или изменении списка во время пагинации. Поэтому ниже
предусмотрены контрольные сверки.

### Начальная загрузка и возобновление

- Существующий архив импортируется в БД отдельно.
- Первая синхронизация начинается **не с текущего времени**, а с момента,
  позволяющего догнать изменения за время создания архива и после него.
- Ориентир — начало исходной полной выгрузки, а не её завершение. Если оно
  неизвестно или не подтверждено, выбирается более ранняя граница и выполняется
  контрольная сверка.
- После отключения сервера процесс продолжает с сохранённой границы и задач,
  а не начинает отсчёт заново.
- Для одного источника допускается только один одновременно выполняющийся
  цикл обнаружения. Обновления одной карточки применяются последовательно,
  чтобы старый ответ не перезаписал более новое состояние.

### Комментарии, вложения и другие связанные данные

Фильтр `updated_after` документирован для карточек. Это **не подтверждает**, что
любое изменение комментария, файла, участника или пункта чек-листа обязательно
изменяет `updated` родительской карточки.

Перед выпуском нужно проверить каждую такую операцию. Если покрытие неполное,
вариант № 1 дополняется исходящими запросами к ленте событий API или отдельной
сверкой соответствующих сущностей. Это по-прежнему периодический опрос,
без обязательного подключения вебхуков. Непроверенные операции нельзя считать
надёжно синхронизируемыми.

У API ленты активности есть фильтры времени и курсорный обход страниц;
владельцу токена нужны права на чтение журнала. Доступность, состав событий
и глубину истории нужно подтвердить в нашем аккаунте.

Источник: [лента активности компании](https://developers.kaiten.ru/activity/list-company-activity).

### Перемещение, архивирование и удаление

- Архивирование учитывается обработкой активных и архивных карточек.
- Перенесённая с выбранной доски карточка может перестать попадать в запросы
  с `board_id=437516`. Поэтому отдельно сверяем состав доски.
- Контрольная сверка получает список ID и нужные метаданные, а не скачивает
  заново подробное содержимое каждого заказа. Частота определяется испытаниями;
  для старта можно рассмотреть ежедневную сверку.
- Отсутствие ID, `403` или `404` не является достаточным доказательством
  удаления: могли измениться права или расположение карточки.
- Такое состояние сначала отмечается как требующее проверки. Исторические
  данные и файлы автоматически не уничтожаются.
- Удаление подтверждается доступным событием/состоянием источника либо отдельной
  процедурой сверки. Полноту событий удаления проверяем отдельно.

### Файлы и ошибки

Сбой API, ограничение частоты и ошибка скачивания получают отдельные статусы,
повторы с задержкой и запись в журнале. Для карточки следует различать хотя бы
«актуальна», «ожидает обновления», «частично обновлена», «ошибка» и
«источник недоступен».

Версии карточки недостаточно, чтобы считать неизменившимися все связанные
сущности. Для них нужны собственные ID, доступные метаданные и, где необходимо,
контрольные суммы. Новая версия файла сохраняется до замены ссылки на неё в
рабочей БД. Порядок очистки старых файлов согласуется с хранением резервных копий.

### Плюсы и ограничения выбранного варианта

Плюсы: работает с локального сервера через исходящие соединения, не требует
адреса приёма запросов из облака, допускает восстановление после простоя.

Ограничения: задержка обновления, дополнительные API-запросы, необходимость
проверять полноту связанных изменений и отдельно сверять состав доски.
Фактическая задержка зависит также от очереди и доступности Kaiten.

## 3. Вариант № 2 — External Webhooks, оставлен альтернативой

### Возможности Kaiten

External Webhooks отправляет POST-уведомления о поддерживаемых событиях
пространства. Предусмотрены `card:add`, **`card:update`**, события комментариев,
файлов, участников и других объектов. Для обновления передаются прежние
данные (`old`), изменённые поля (`changes`) и автор (`author`).

Вебхук настраивается на уровне пространства, поэтому принимающий обработчик
должен учитывать нужные доски. Обычный раздел Kaiten «Webhooks» для создания
карточек извне — другой механизм; для обновления нашей копии нужны именно
**External Webhooks**.

Источники: [External Webhooks](https://developers.kaiten.ru/external-webhooks),
[событие card:update](https://developers.kaiten.ru/external-webhooks/card/card:update),
[настройка в интерфейсе](https://faq-ru.kaiten.site/external-webhooks).

### Предлагаемая обработка

1. Kaiten отправляет уведомление в наш отдельный HTTPS-обработчик.
2. Обработчик проверяет допустимость запроса и формат события, извлекает ID
   объекта по схеме конкретного типа и надёжно сохраняет задачу в БД.
3. После сохранения быстро возвращает успешный ответ. Массовая работа с файлами
   внутри запроса вебхука не выполняется.
4. Фоновый процесс получает актуальные данные карточки/раздела через API и
   применяет их тем же механизмом, что используется в варианте № 1.
5. Повторные уведомления не создают дубликаты. Очередь объединяет совместимые
   задачи одного объекта; позднее уведомление не откатывает текущее состояние.

Событие используется прежде всего как **сигнал обновления**. Не предполагаем,
что его payload содержит всё содержимое карточки и все вложения.

### Условия подключения и ограничения

- Облачный Kaiten должен иметь сетевой доступ к URL обработчика. Обычный адрес
  внутри локальной сети для этого не подходит.
- Способ доступа согласуется отдельно: например, отдельный приёмный шлюз.
  Доступ извне нужен обработчику событий, а не PostgreSQL.
- Доступные способы проверки отправителя, правила повторных доставок,
  таймауты и порядок событий нужно проверить перед реализацией. Не предполагаем
  наличие подписи, гарантированной повторной доставки или строгого порядка,
  если это не подтверждено для нашего подключения.
- Нельзя считать весь поток изменений покрытым одним `card:update`: изменения
  связанных сущностей имеют отдельные события.
- В опубликованном каталоге нет отдельного `card:remove`; покрытие удаления
  карточек и прочих операций требуется подтвердить испытаниями.
- Периодический опрос и контрольная сверка сохраняются как восстановительный
  механизм после простоя или пропущенных уведомлений.

Плюсы: возможность быстрее реагировать на изменения и сократить регулярные
запросы обнаружения. Ограничения: входящая доступность сервера, дополнительная
настройка приёма событий и необходимость обрабатывать повторы и пропуски.

## 4. Общее устройство двух вариантов

Различается источник сигнала, а не применение изменений:

```text
Таймер и API (вариант 1) ────┐
                            ├→ очередь PostgreSQL → обработчик обновления
External Webhooks (вариант 2)┘                           ↓
                                                 рабочие данные
                                                 и хранилище файлов
                                                        ↓
                                                   веб-интерфейс
```

Это проектная схема, не перечень уже существующих модулей. Отдельный брокер
сообщений на старте не обязателен: достаточно устойчивой очереди в PostgreSQL,
если она обеспечивает надёжное получение задач, повторы и защиту от параллельной
обработки одного объекта.

Нужно будет хранить настройки источника и область синхронизации, временные
границы обнаружения, очередь, результаты применения, источник/версию/время
состояния карточки и диагностические сведения. Точную схему таблиц определяем
после готовности рабочей модели доски.

## 5. Условия начала реализации и критерии проверки

К реализации возвращаемся, когда:

1. Подключён и проверен PostgreSQL, подготовлены миграции рабочей доски.
2. Завершён начальный импорт и определено хранение вложений.
3. Готов веб-интерфейс просмотра рабочих карточек и отображения проблем.
4. Согласовано, что Kaiten — главный источник на переходный период.

Минимальные испытания:

| Сценарий в Kaiten | Что проверяем у нас |
| --- | --- |
| Создание карточки | Появляется одна новая запись |
| Изменение названия, описания, срока, меток | Обновляется существующая запись |
| Добавление/изменение/удаление комментария | Отражается соответствующее состояние |
| Изменение участников и пунктов чек-листа | Обновляются связанные данные |
| Добавление/изменение/удаление вложения | Корректны файл, метаданные и историческое сохранение |
| Перемещение внутри доски | Меняется расположение |
| Перемещение на другую доску | Нет ложного удаления; отражается смена области |
| Архивирование и возврат | Сохраняется правильный статус |
| Удаление либо потеря доступа | Состояния различаются; история сохраняется |
| Более 100 изменений и изменения во время обхода | Проверяются страницы, границы и контрольная сверка |
| Несколько изменений в одну секунду | Изменения не теряются на границе окна |
| Повторное получение тех же данных | Нет дубликатов и отката состояния |
| Отключение сервера, API или скачивания | После восстановления очередь догоняет источник |
| Сбой после получения страницы, но до фиксации задач | Окно безопасно повторяется |

Проверяем также, что обновление 10 карточек не вызывает повторного скачивания
содержимого всех 20 тысяч заказов. Контрольная сверка списка ID допускается.

## 6. Синхронизация и резервные копии

Синхронизация поддерживает текущее рабочее состояние. Резервная копия позволяет
вернуться к прошлому состоянию. Ошибка или удаление в Kaiten не должны лишать
нас возможности восстановить прежние данные.

Исходные архивные снимки не переписываются каждым циклом обновления. Для
рабочей БД и вложений предусматриваются отдельные согласованные резервные
копии и проверка восстановления.

**Итог решения:** после готовности БД и интерфейса сначала реализуем вариант
№ 1. Вариант № 2 остаётся документированным расширением того же механизма
обновления. Сейчас этот документ не добавляет задания по расписанию, фоновые
процессы, маршруты вебхуков или настройки в аккаунте Kaiten.
